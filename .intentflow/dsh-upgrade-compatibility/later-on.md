# 后续想法备忘 — dsh-upgrade-compatibility（第二迭代）

> 设计阶段识别但**此时不做**的事项，以及未来演进方向。只记录想法，不做任何设计预留——需要时直接实现。

## 想法列表

- **L01**：日志/诊断体系
  - 现状：用户在设计启动时明确「没必要做日志」，故本轮不做任何日志增强，仅保留现有 `showErrorMessage` 弹错。
  - 何时做：当再次出现「命令无反应且无法定位」且弹错不足以定位时。
  - 备注：方向是让 open/stop 各环节（settings/定位/端口判定/spawn/等待端口）在 Output「DSH」频道留痕，而非本轮范围。

- **L02**：契约探测（spawn 前跑 `dsh web --help` / `--dump-config` 探测支持的 flag）
  - 现状：决策 2 已选「最小稳定参数集 + 单测锁死」，不引入探测，避免每版 dsh 还要维护探测逻辑。
  - 何时做：若 dsh 后续高频变更 CLI 且单测锁死＋改一处都不够跟时。
  - 备注：探测结论需进程级缓存，避免每次 open 多一次 spawn。

- **L03**：dsh 版本感知分支
  - 现状：决策 2 已否掉，因「版本→参数」映射表同样需要随 dsh 升级维护。
  - 何时做：若 dsh 出现「同参数在不同版本语义冲突」且无法用单一稳定集覆盖时。
  - 备注：版本来源可用 `dsh --version`。

- **L04**：全走 shim 后的 Windows 转义风险回退
  - 现状：决策 1 改以 `dsh.cmd` shim 为稳定入口（`shell:true`）。若日后用户工作区/补丁路径含空格或特殊字符导致 `.cmd` 转义异常，可回退为「读 package.json bin 定位真实入口后 `node + 真实入口` 直跑」。
  - 何时做：实测出 `.cmd` 转义导致的 spawn 失败时。
  - 备注：`buildDshArgs` 用 args 数组 + `needShell` 已尽量规避；本项为被动回退预案，非主动预留。

## 与当前设计的关系（轻量提示）

- L01 不影响当前接口，届时在 manager 各环节加 `log()` 即插即用。
- L02/L03 若落地会改 `buildDshArgs` 的先后关系，当前签名无需提前预留。
- L04 只影响 `detect.resolveDsh` 的返回形态（`{command, prefixArgs}` 已足够承载两种形态），无需改契约。
